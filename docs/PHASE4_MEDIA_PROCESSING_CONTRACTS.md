# Phase 4 — Media Processing Contracts and Integration Foundations

The backend-independent types in `ai_engine.media_processing` define the data
boundary between media storage/upload and future AI workers. They do not depend
on FastAPI, SQLite, a queue, or any image-processing library.

- `ImageMetadata` carries the uploaded media identity, investigation identity,
  validated image dimensions and MIME type, byte size, SHA-256, original display
  filename, and UTC upload time.
- `MediaInput` pairs that metadata with bytes for an in-process consumer. A
  future queue adapter should pass a private storage reference and load bytes at
  the worker boundary instead of serializing image bytes into job metadata.
- `ProcessingJob` describes job identity, media/investigation association,
  lifecycle status, timestamps, and an optional structured failure.
- `ProcessingResult` records algorithm identity/version and typed result data.
- `DerivedMediaReference` records the source relationship and transformation
  provenance for future derivative assets.
- `ProcessingFailure` carries a safe stable code, human-readable message, and
  UTC occurrence time; API-specific error envelopes remain the backend's job.

Statuses are `received`, `queued`, `processing`, `completed`, `failed`, and
`skipped`. Stage 1 only defined and validated contracts. Stage 2 adds in-memory
image preprocessing: it checks dimensions before pixel decoding, applies EXIF
orientation, converts to RGB, composites transparency over white, and encodes
JPEG without resizing. It returns bytes and a `DerivedMediaReference`; it does
not persist derivatives or mutate source bytes. Phase 3's upload response and
database schema remain unchanged; an adapter maps its `checksum` and `filename`
fields to the AI-side `sha256` and `original_filename` names.

## Stage 3 — Image intelligence

`compute_phash` calculates a versioned 64-bit DCT perceptual hash from the
Stage 2 normalized JPEG. The pHash is separate from the source SHA-256. Hash
comparison reports Hamming distance and the heuristic score
`1 - hamming_distance / 64`. `find_near_duplicates` applies a configurable,
inclusive minimum-similarity threshold and returns source/matching media IDs,
scores, and derived-media IDs for traceability. Similarity is not a probability;
hashes generated by different algorithm versions cannot be compared. This
stage does not process video, enqueue work, or add frontend behavior.

## Package 2 — Processing and integration foundation

`MediaProcessingPipeline` coordinates the current normalization and pHash
stages through `received`, `queued`, `processing`, and a terminal
`completed`/`failed` state. Explicit skips use `skipped`. It records UTC job and
attempt timestamps, safe failures, result records, and retry history. Within a
single process, a job ID is serialized and completed executions are reused;
failed work retries only when explicitly requested. State is in-memory and is
not a durable queue or cross-process lock.

`MediaEvidenceReference` connects investigation, original media, source
SHA-256, derived media, derivative SHA-256, pHash/version, and transformation
version. It is provenance only: it does not assign an evidence stance,
reliability, or relevance. `verify_claim_with_media_references` delegates only
explicitly supplied `Evidence` values to the existing verifier, so media alone
cannot produce a factual verdict.

`media_input_from_phase3_upload` accepts exactly the nine success fields
documented by Phase 3 and the original bytes supplied by its caller. It is a
pure adapter and performs no HTTP request. It rejects undocumented fields and
validates the response checksum against those bytes.

The available local backend is the provisional Phase 2 API; it exposes no
media-upload, processing-job, failure, or result endpoints. The Phase 3 spec
confirms only the upload endpoint/response and does not specify processing
status retrieval. The Step 4 preparation below defines a separately versioned
proposal and disabled client boundary; it does not make these routes available.

## Step 3 — Upload-to-AI workflow

`process_phase3_upload` composes the strict response adapter with the in-process
job pipeline. It verifies the upload metadata against original bytes, runs
normalization and versioned pHash, optionally compares supplied existing hashes,
and returns the processing job, unified `ProcessingResult`, normalized image,
similarity matches, provenance reference, and safe failures. It never changes
the original byte string. `retry_failed=True` is required to retry a failed job.
The workflow does not request the upload or query a backend, and it does not
create claim-verification evidence or verdicts from media alone.

No video decoder package (`av`, `cv2`, `ffmpeg`, `imageio_ffmpeg`) or `ffmpeg`
executable is available in the inspected environment. `video.py` therefore
defines validated source/frame contracts, sampling configuration, provenance
checks, and a `VideoFrameExtractor` protocol only. It does not decode video.

## Step 4 — Processing API and frontend preparation

`PHASE4_PROCESSING_API.md` defines the separately versioned v1.0
processing-job, status, result, failure, retry, and error-envelope contract.
The provisional member-2 backend implements it. Cross-branch approval and the
Phase 3 media storage adapter remain integration dependencies. The frozen
Shared API Contract v1.2 and Phase 3 media upload specification remain
unchanged.

`processing_api.py` defines request/response dataclasses and a
`ProcessingApiAdapter` protocol for a future backend adapter. Its default
`UnavailableProcessingApiAdapter` raises `ProcessingApiUnavailable` and never
creates in-memory placeholder jobs or results. The frontend has matching
runtime-validated TypeScript contracts and a route client that is disabled by
default. `ProcessingPanel` can render server-provided lifecycle, failure, retry,
and result data, but is not mounted on the dashboard because the current API
cannot supply those fields. Its progress display is a lifecycle timeline only;
there is no invented percentage or stage-progress measurement.

The remaining backend dependency is Ram's approved media storage integration.
The local implementation has persistent job and result storage, but it cannot
load original media until an adapter for the approved private storage is
supplied. The frontend service remains disabled until that integration and
cross-branch contract agreement are complete.
